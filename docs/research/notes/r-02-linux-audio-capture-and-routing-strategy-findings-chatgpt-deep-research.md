# R-02 Linux audio capture and routing strategy

## Bottom line

The PoC should be explicitly **PipeWire-first** for `online_dual_stream`. The most reliable pattern is a **session-scoped dedicated meeting sink** for the meeting app’s playback, capture of that sink’s **monitor** as the remote stream, direct capture of the chosen microphone as the local stream, and a separate loopback from the meeting sink to the user’s actual speakers or headphones so the call remains audible. That pattern matches PipeWire’s graph model, uses monitorable sink nodes that the session manager understands, and avoids turning the canonical remote artefact into “whatever the whole desktop happened to play”. PipeWire exposes nodes, ports and links as a routing graph, supports monitor ports on sinks, can build virtual sinks and sources via loopback, and its PulseAudio-compatible layer still supports the `pactl` tooling and built-in modules that common desktop apps expect. citeturn2view0turn2view1turn2view2turn4view1turn4view2turn11search2

The **second-best alternative** is separate microphone capture plus capture of the **current default sink monitor**, with no dedicated reroute. It is simpler to set up, but it is materially less reliable for product goals: notification sounds, unrelated music, browser audio, and default-device changes can all contaminate or redirect the “remote” track. That makes it an acceptable fallback path, but a poor primary design for a product whose highest priority is durable, debuggable recording. citeturn2view2turn12search1

`in_person_single_mic` looks **incremental rather than materially different** if the adapter contract is changed now from “one generic capture port” to “one capture session that may yield one or more source streams”. The hard Linux-specific problem is not microphone recording; it is controlled desktop routing and source creation for `online_dual_stream`. Once that exists, the single-room-mic profile reuses most of the same writer, sealing, crash-handling, and replay machinery while dropping most of the routing complexity. Confidence is high on that stack recommendation, and only moderate on fully automatic playback-stream identification for browser-based meetings, because Linux routing works at stream and node granularity and the exact stream layout depends on the client. citeturn19search7turn2view0turn22view0turn16view3

## Safe Linux assumptions for the PoC

A safe assumption for a **desktop PoC** is that there is a **user-session sound server**, and that on mainstream current desktop setups it is usually **PipeWire with WirePlumber**, often with the **PipeWire PulseAudio compatibility layer** enabled. PipeWire’s own architecture is a graph-based media server that accommodates ALSA, PulseAudio and JACK clients, while WirePlumber is normally run as a user-session service and manages linking and policy on top of that graph. Contemporary desktop distributions have largely converged on this model, even though edge cases still exist. citeturn2view0turn15search2turn15search3turn16view2turn5search2turn16view3

A safe assumption is **not** that direct ALSA is enough for `online_dual_stream`. ALSA’s `dmix` and `dsnoop` plugins can share playback and capture devices, and `.asoundrc` can describe complex virtual devices, but that is still device-level plumbing rather than a practical, debuggable, per-application desktop routing strategy. For the PoC, ALSA should be treated as the hardware layer that sits **under** the adapter, not as the primary control plane for meeting playback isolation. citeturn7search1turn8search3turn8search2turn2view0

A further safe assumption is that the adapter can **standardise internally on 48 kHz** capture requests without forcing the user’s whole graph into a new rate. PipeWire’s default graph clock rate is 48 kHz, and its PulseAudio-compatible layer documents 48 kHz as the relevant fixed-rate quirk value, but forcing the global graph clock at runtime affects the whole user session and should not be the PoC’s normal behaviour. Request 48 kHz for the capture streams; do not try to reconfigure the user’s whole desktop audio graph just to satisfy the recorder. citeturn17search1turn22view0turn15search4

The practical support boundary should therefore be narrow. Treat **PipeWire user-session desktops** as supported for `online_dual_stream`, treat **real PulseAudio** as a compatibility path if encountered, and treat **ALSA-only or headless/minimal environments** as out of scope for that profile. That keeps the tester burden realistic and aligns with the product’s priorities of robustness and debuggability over breadth. citeturn4view2turn16view2turn15search3

## Recommended pattern for `online_dual_stream`

The concrete routing pattern should work like this.

- **Discover, then require explicit selection.** Enumerate active playback streams, the current output sink, and available input sources in the user session. Surface stable human-facing identifiers such as application binary, stream name and media name, and let the CLI confirm which playback stream is the meeting audio. PipeWire exposes application properties for matching, and graph tooling exposes media names and node state for inspection. citeturn22view0turn16view3turn13search0

- **Create a dedicated session sink for meeting playback.** The key product primitive is a sink that exists only for this capture session, not a permanent desktop reconfiguration. In practice this can be realised as a dedicated null sink or other virtual sink in the user session. PipeWire’s PulseAudio layer supports built-in module loading through `pactl`, and the relevant null-sink module is documented and unloadable at runtime. citeturn4view1turn4view0turn22view0

- **Capture that dedicated sink’s monitor as the remote stream.** Monitor ports are created on sinks by default, and the loopback documentation explicitly supports capturing sink monitor ports. This gives the recorder a clean remote artefact that tracks only what was routed through the meeting sink, not all desktop output. citeturn2view2turn2view1

- **Create a separate loopback from the meeting sink to the user’s actual playback device.** This is important. It decouples the remote recording path from the physical speaker or headset path. If the user’s headphones disappear or they switch from speakers to a headset, the recorder’s remote stream still exists on the dedicated sink even if the “audible to the user” loopback needs to be recreated. That is more robust than recording the physical sink directly. PipeWire’s loopback module is designed to connect arbitrary capture and playback streams and to create virtual sinks and sources that the session manager can manage. citeturn2view1turn19search6

- **Move only the chosen meeting playback stream into that sink.** Do not implement the feature by changing the system’s default sink. WirePlumber restores and follows defaults in PulseAudio-compatible ways, which is useful for normal desktop audio but risky for a recorder, because unrelated streams may follow default-target changes. Use explicit per-stream movement instead, via `target.object` semantics or `pactl move-sink-input`, so the routing remains narrowly scoped and observable. citeturn2view2turn2view3turn11search2

- **Capture the microphone directly as a distinct source.** For the canonical local-user track, prefer the selected physical source rather than optional conferencing DSP such as echo-cancel or suppression nodes. PipeWire supports echo-cancel virtual sources for conferencing, but that adds more virtual-node policy and a less transparent debugging surface. For this PoC, raw microphone capture is the better default. citeturn19search9turn4view3

This pattern remains the right one even when the implementation path uses the PulseAudio compatibility layer for stream movement, because the product-level strategy is still PipeWire-centred: a per-session graph object is created, explicitly routed, monitored, recorded, and then torn down. The compatibility layer is a control convenience, not the conceptual model. citeturn4view2turn15search2turn19search7

## Failure modes and fallback policy

The first important failure mode is **stream-selection ambiguity**. Linux can move and capture streams, but it does not understand the product concept of “the meeting” unless the chosen conferencing client exposes that as a distinct playback stream. The least predictable cases are browser-based meetings and multi-stream desktop apps. The mitigation is to make stream choice explicit in the CLI, show the chosen application and media metadata before starting, and record the resulting graph binding in a sidecar event log. Automatic heuristics can help, but they should not be the sole decision-maker. citeturn22view0turn16view3turn13search0

The second is **device churn**. Microphones get unplugged, Bluetooth headsets disappear, and users switch outputs mid-session. A dedicated meeting sink plus a separate speaker loopback handles output churn much better than direct physical-sink recording, because the remote recording source remains the session sink monitor even when the audible-output loopback needs work. For microphone loss, the worker should continue sealing the remote artefact and emit a degraded state rather than tearing down the whole session. WirePlumber’s linking policy can reconnect or fall back by default, but those behaviours are exactly why the recorder should pin and log its own explicit capture topology rather than trust ambient defaults. citeturn2view3turn14search0turn2view1

The third is **default target churn caused by user actions**. WirePlumber’s default behaviour is compatible with PulseAudio expectations: manually moved targets can be restored, and streams that follow the default target can move again if the default changes. That is right for a desktop, but wrong for a recorder that needs stable semantics. The mitigation is simple: never implement the PoC by swapping the system default sink or source; move only the selected meeting stream and bind the recorder to explicit source nodes. citeturn2view2turn12search1

The fourth is **server or session-manager failure**. PipeWire and WirePlumber are separate user-session processes, and PipeWire exposes monitoring tools that can stream graph-state changes as JSON. The capture worker should therefore treat graph loss, broken links, or a disappeared session sink as observable state changes, not mysterious audio silence. When that happens, it should keep already written audio intact, mark the current segment as degraded, and either continue with the surviving stream or fall back according to policy. The recorder should never depend on downstream transcription or orchestration success to preserve captured audio. citeturn15search2turn15search3turn13search0turn10search12

The fifth is **client quirks and over-aggressive low-latency settings**. PipeWire’s PulseAudio layer already documents application-specific quirks for some conferencing-related clients, including format shims and options to block client-controlled source volume changes, and it explicitly documents that smaller request, fragment and quantum sizes trade lower latency for higher CPU overhead. For a meeting-note recorder, that points to a conservative policy: prefer default or slightly conservative buffering, avoid “pro-audio” tuning, and only add client-specific quirks when field evidence shows they are needed. citeturn22view0

Fallback behaviour should be **tiered and explicit**. If dedicated routing fails, fall back first to `mic + default_sink_monitor` and mark the session metadata as `system_mix_remote`; if system-audio capture is impossible, fall back to `mic_only` and mark the session as degraded rather than pretending it is still dual-stream. If the session starts correctly and later degrades, continue recording surviving streams, write gap or degradation events, and never discard already sealed audio. That is the behaviour most consistent with the fixed constraints. citeturn2view2turn13search0

## Implications for the capture worker boundary and profile model

The Linux adapter boundary should include **routing control as part of capture setup**, not as a separate concern. On Linux, the remote capture source for `online_dual_stream` is not just “an input device”; it is a **source created by routing policy** inside the user’s audio graph. That means the adapter’s job is to produce a capture topology: selected microphone source, dedicated meeting sink, remote monitor source, speaker loopback, and the bindings between them. PipeWire’s own session-management docs distinguish between the low-level media graph and the higher-level session graph precisely because the routing policy is a separate conceptual object. citeturn19search7turn2view0

That leads to the core architectural answer: **keep one capture abstraction, but retire the single generic capture-port assumption** if that assumption means “exactly one homogeneous input”. A better contract is a **capture session plan** that can yield one or more canonical source artefacts plus routing metadata. Under that contract, `online_dual_stream` is a two-source topology with routing state, while `in_person_single_mic` is a one-source topology with no routing state. Both still fit beneath one higher-level adapter boundary, and the core pipeline remains portable because it only needs source-role labels, artefact descriptors, timing metadata, and degradation events. citeturn19search7turn15search2

Within the capture worker, separate the **real-time recorder path** from the **routing supervisor path** even if both remain in the same process for the PoC. The recorder owns the file descriptors, append-only writes, sealing and crash-bounded persistence. The routing supervisor owns graph discovery, sink creation, movement of playback streams, and event logging. That separation makes it much easier to satisfy the fixed requirement that downstream failures must not corrupt already captured audio. The practical shape is one worker process with two responsibilities, not one undifferentiated “capture port”. citeturn15search2turn13search0

## Testing and fixtures

The architecture should anticipate two very different testing layers. First, **pipeline and replay tests** should run from sealed audio artefacts only, with no dependency on the live Linux stack. That is the cleanest way to protect transcription, diarisation, correction and notes generation from capture-layer churn. Second, **adapter integration tests** should run against a disposable PipeWire user session with synthetic nodes, virtual sinks and explicit graph inspection. PipeWire’s tools already support targeting specific nodes for capture and dumping or monitoring the live graph as JSON, which is exactly what an adapter test harness needs. citeturn12search0turn13search0turn13search7

The fixture strategy should therefore include reproducible cases for: correct dual-stream routing; default-sink-monitor fallback; unrelated desktop audio on the default sink; microphone disconnect and reconnect; playback-device churn; meeting-app restart with a new stream; server or session-manager restart; and high-latency or virtual-machine environments. PipeWire and WirePlumber provide the observability needed to make those failures diagnosable: `pw-dump --monitor` for state changes, `pw-top` for driver and follower timing, `pw-mon` for object-level monitoring, and detailed WirePlumber journal logging when debug topics are enabled. For synthetic fixtures, PipeWire’s own examples use generated audio sources such as `audiotestsrc`, which is useful for deterministic integration tests. citeturn13search0turn13search8turn10search12turn15search6turn21search0

For tester support, the PoC should emit a small **support bundle** on failure: capture profile, selected source and sink names, routing events, degraded-state transitions, and a snapshot of the live graph. That makes CLI operation practical without asking testers to understand a full patchbay. The goal is not to hide Linux audio reality; it is to make it inspectable in the product’s own terms. citeturn13search0turn12search1turn15search6

## Assessment of `in_person_single_mic`

Adding `in_person_single_mic` after `online_dual_stream` is **not a second routing architecture**. It is the simpler case. The single-mic profile reuses device discovery, source selection, file writing, crash handling, preflight metering, sidecar event logging, artefact sealing and replay. What disappears is most of the Linux-specific routing complexity: no dedicated meeting sink, no playback-stream move, no speaker loopback, and no concept of “perfect remote isolation” to preserve. In runtime terms it is materially simpler; in implementation terms it should be a modest extension of the same adapter family. citeturn2view0turn15search2

There is one caveat. Single-room-mic capture stays incremental **only while the profile really means one chosen source**. If later work expands into multi-channel USB interfaces, beamforming arrays, channel remapping, or multiple room microphones, the profile starts to look more like a topology problem again. PipeWire’s loopback examples already show virtual-source creation and downmixing from multichannel inputs, which means the stack can support that future, but it also shows where the complexity returns. For the current PoC definition, though, `in_person_single_mic` is incremental and should remain under the same adapter boundary. citeturn2view1turn8search3
