# R-04 ASR Provider Strategy

## Recommendation

The best fit for the current PoC is a **Whisper-family local ASR strategy behind the existing provider port, with `faster-whisper` as the primary provider runtime**. If one operational default checkpoint is needed to unblock implementation, use **`large-v3-turbo`** as the standard run target and keep **`large-v3`** available as a higher-cost quality-reference rerun on stronger machines. That choice stays fully local, preserves broad multilingual coverage, fits Linux automation well, and gives a practical API surface for timestamps, VAD, prompting, hotword hints, and repeatable reruns from canonical audio. Whisper’s training regime was explicitly built for robustness across accents, background noise, and technical language, and the current model family still offers much broader language coverage than the more specialised open alternatives. citeturn22view0turn25view0turn16view0turn10view4

The reason not to make `large-v3` the universal PoC default is hardware burden. The upstream Whisper docs put the **large** checkpoint at roughly **10 GB VRAM** and **turbo** at roughly **6 GB VRAM**, while `faster-whisper` documents both GPU and CPU INT8 execution paths and materially better runtime than the reference `openai/whisper` implementation on its published benchmarks. For a privacy-first, post-meeting workflow where weaker tester machines matter and strict low latency does not, a **tiered Whisper strategy** is safer than binding the whole PoC to one heavyweight checkpoint. citeturn32view0turn20view2

A practical shortlist follows naturally from that choice. The **primary path** should be `faster-whisper`; the **strongest fallback** should be `whisper.cpp`; the **conditional specialist challenger** is entity["company","NVIDIA","gpu company"] Parakeet via NeMo if scope later narrows to English or standardised NVIDIA GPU hardware; and **Vosk** belongs only on the emergency low-spec shortlist. citeturn19view1turn10view3turn29view0turn6view3

## Why this is the best fit

For real meeting audio, there is no open local model family that is clearly superior on *all* of your priorities, but the entity["company","OpenAI","ai company"] Whisper family remains the safest generalist choice. Whisper was trained at very large scale and was explicitly presented as more robust to accents, background noise, and technical language than narrower ASR systems. The current `large-v3` card also keeps **99-language** coverage and reports broad gains over `large-v2`. Separately, Speech Robust Bench found Whisper to be the most robust model on average among the tested English ASR systems, and that benchmark includes difficult near-field and far-field conversational sources such as AMI and CHiME-6, which are much closer to meeting conditions than clean read speech. citeturn22view0turn25view0turn13view0

`faster-whisper` is a better PoC runtime than the reference Whisper package because it gives a more practical Linux operator surface. Its docs expose **word timestamps**, **Silero-based VAD filtering**, **initial prompts**, **hotword hints**, **CPU and CUDA device selection**, and a **`local_files_only`** option for pre-seeded model caches. It also avoids a separate system `ffmpeg` dependency by using PyAV, whereas the upstream `openai/whisper` README still documents `ffmpeg` as a required system tool. That is exactly the kind of operational simplification that matters in a local-only PoC where automation, reproducibility, and representative tester machines matter more than model elegance. citeturn16view0turn20view2turn32view0

It also matches the architecture you described better than a single-engine commitment. `faster-whisper` can load converted Whisper-compatible models from a **local directory**, automatically download converted models when required, and work in a locked-down mode if weights are pre-cached. That makes it straightforward to preserve the provider abstraction, rerun from canonical audio, and compare checkpoints or decode settings without changing the rest of the pipeline. It also puts soft vocabulary biasing in the ASR layer through prompts and hotwords, while still leaving room for later checkpoint swaps or fine-tuned Whisper-compatible models if the PoC reveals a very specific domain vocabulary problem. citeturn20view1turn16view0

## Alternatives and why they lost

The **strongest alternative** is **`whisper.cpp`**. It is extremely attractive for this PoC because it is a plain C/C++ implementation with no heavyweight runtime dependency chain, supports Linux well, exposes a C-style API, supports CPU-only inference, and supports integer quantisation. Its published memory table is also favourable for weaker machines: the repository lists roughly **~852 MB** memory for `small`, **~2.1 GB** for `medium`, and **~3.9 GB** for `large`, before further reductions from quantisation. That makes it the most credible **secondary provider** when the hardware risk is more important than the primary runtime ergonomics. citeturn19view1turn19view0turn24view3

It loses the primary slot only narrowly, and mainly on workflow fit rather than on principle. For this PoC, the first provider should make it easy to drive **timestamps, VAD, prompt biasing, hotword hints, batched transcription, model conversion, and rerun controls** from an automated test harness and correction workflow. `faster-whisper` exposes those controls directly and explicitly in the runtime surface documented today. So the right ordering is **`faster-whisper` first, `whisper.cpp` second**. If early validation shows that CPU-only or no-CUDA environments are the dominant risk, that ordering can be swapped without changing the architecture. citeturn16view0turn20view1

The best **non-Whisper-family contender** is Parakeet through NeMo. On the 2026 ASR Leaderboard paper, **Parakeet TDT 0.6B v2** ranks ahead of Whisper `large-v3` on the short-form English average WER and does so with a dramatically higher reported RTFx, while **Parakeet TDT 0.6B v3** stays competitive on long-form English and is much faster than Whisper there as well. NeMo also has a substantially stronger customisation story than Whisper, with explicit **word boosting** and **language-model fusion** support, including for **TDT** models. On paper, that is impressive. citeturn10view3turn10view4turn29view0turn29view1

Parakeet still loses for the current PoC because its operational assumptions do not line up as cleanly with your constraints. **v2 is English-only**; **v3 expands to 25 European languages but gives up some English accuracy to do that**; the ecosystem is more GPU-centric; and the official model cards discuss long-audio behaviour in terms of **A100 80GB** examples and GPU-accelerated deployment. That makes Parakeet a very plausible later-stage evaluation target if the product scope hardens to English and standardised NVIDIA hardware, but not the best first PoC default for a privacy-first local notes tool that has to survive weaker representative machines. citeturn5view7turn17search3turn18search0turn25view2

Vosk is worth keeping in the shortlist only for a different reason: it is lightweight and unusually strong on deterministic vocabulary handling. The official Vosk material stresses offline operation on lightweight devices, small portable models, and runtime vocabulary adaptation, and its adaptation guide goes much further than Whisper-style hinting by supporting runtime word lists, offline language-model rebuilding, and acoustic-model fine-tuning. That is useful if the defining problem becomes **ultra-low hardware footprint** or **tight vocabulary control**. It is not the right primary strategy for this PoC, whose top-ranked requirement after local-only operation is **transcription quality on real meeting audio** rather than the most configurable decoder. citeturn6view3turn6view4turn5view8

## Operational assumptions and maintainability

The recommended path assumes **Linux**, **Python 3.9+**, and two supported execution modes: a documented **CUDA path** or a slower **CPU fallback**. In `faster-whisper`, the current documented GPU route still centres on **CUDA 12** and **cuDNN 9**, with explicit downgrade guidance for older CUDA 11 / cuDNN 8 environments. On the CPU side, the library explicitly supports INT8 execution. Model files are automatically downloaded when referenced by size or hub ID unless they are pre-seeded locally, and the API exposes `local_files_only` specifically for local-cache operation. In other words: **audio stays on the machine**, but truly offline or air-gapped installs still require a deliberate model-caching step during setup. citeturn20view2turn16view0turn20view1

Runtime burden is manageable only if the PoC is honest about checkpoint tiers. The upstream Whisper docs describe `turbo` as an optimised `large-v3` variant with faster transcription and only minimal accuracy degradation, while placing its memory demand well below full large. `faster-whisper`’s own published benchmarks, run on specific hardware, show a large speed advantage versus the reference implementation and a viable CPU path for smaller checkpoints, but they do **not** remove the basic truth that big checkpoints on weak CPUs will be slow. An important escape hatch inside the same provider strategy is **Distil-Whisper**: its authors report a model that is **much faster**, **about half the size**, within **about 1% WER** on long-form, and less prone to long-form hallucinations, albeit **English-only**. That makes it the most credible checkpoint-level relief valve if runtime pain becomes serious before multilingual scope is fixed. citeturn32view0turn20view2turn6view1turn6view0

Near-term maintainability looks **good enough** for the PoC horizon, but the real risk is **dependency drift**, not abandonment. The upstream Whisper repo published a release in **June 2025**; `faster-whisper` published releases through **October 2025**; `whisper.cpp` published a release in **March 2026**; and CTranslate2 was still shipping feature and compatibility updates in **2026**. That is a healthy enough maintenance story for a PoC. The reason to pin versions anyway is that these projects move, and the breakage mode is usually packaging or dependency compatibility, not model quality. By contrast, Vosk’s maintenance surface looks less reassuring for a new default pick, with a February 2026 issue noting that the PyPI package lagged the newer repository release. citeturn24view2turn24view0turn24view3turn33view0turn23view0turn6view9

## Architecture implications and owned risks

The provider abstraction should assume from day one that **ASR output is provisional and replayable**. Conversational ASR is still difficult because of **overlapping speech**, **far-field noise**, and changing speaker counts, and robustness falls as overlap and speaker complexity increase. That means the architecture should preserve raw audio as the canonical source, persist provider metadata with every generated transcript, and make reruns with alternate checkpoints or decode parameters first-class operations. The correction overlay should remain separate from generated ASR text exactly as your baseline already assumes, because no model choice removes this class of failure. citeturn12view1turn13view0

A second owned risk is **long-form failure behaviour**. `faster-whisper` explicitly documents that turning off `condition_on_previous_text` can make output less consistent across windows but also less prone to repetition loops and timestamp drift, and it exposes a `hallucination_silence_threshold` specifically for suspected hallucination cases. Distil-Whisper was motivated in part by the same issue and reports lower hallucination rates on long-form audio. That is a strong signal that the architecture should treat decode settings as part of the replay surface, not as hidden implementation details. If a transcript looks suspicious, the system should make it cheap to rerun from audio with a different checkpoint or different long-form settings rather than pretending one pass is authoritative. citeturn16view0turn6view0

User-supplied vocabulary is the main place where model choice should **not** be asked to do too much. In the Whisper-family stack, `initial_prompt` and `hotwords` are useful, but they are still **soft biasing tools**, not deterministic lexicon control. If the long-term product requirement becomes “the model must reliably recognise our custom proper nouns, acronyms, and project names with strong biasing”, then NeMo and Vosk offer materially stronger decoder-level customisation options through word boosting, language-model fusion, or explicit vocabulary adaptation. For the current PoC, though, that requirement is better handled by a combination of **prompt hints**, **correction UX**, **provider metadata for replay**, and **test corpora containing representative jargon**, rather than by changing the primary ASR family now. citeturn16view0turn29view0turn5view8

One more implication follows from language uncertainty. Whisper still offers the broadest language safety margin among the realistic local options discussed here, with **99-language** support; Parakeet’s multilingual v3 is narrower, and Distil-Whisper is English-only. So if the PoC may encounter multilingual or code-switched meetings before scope is frozen, the architecture should keep the default provider in the Whisper family and treat any English-specialised checkpoint as an optimisation, not the baseline assumption. citeturn25view0turn25view2turn6view1

## Validation on representative hardware

Validation should be framed around **hardware tiers**, not just one favourite laptop. The upstream Whisper docs make the `turbo` versus `large` memory gap large enough to matter in practice, so the PoC should be tested on at least a stronger NVIDIA GPU machine, a middling tester machine, and a weak or CPU-only machine before the ASR defaults are treated as stable. citeturn32view0

A useful validation sequence is short and concrete. First, assemble a small meeting corpus that reflects the actual failure modes the product will face: one cleaner near-field meeting, one noisier or farther-field meeting, one overlap-heavy meeting, and one jargon-heavy meeting; add non-English or code-switched material if that is even plausibly in scope. Second, run the same source audio through four configurations: `faster-whisper` with `large-v3-turbo`, `faster-whisper` with `large-v3` on the strongest machine only, an English-only runtime-relief option such as Distil-Whisper if applicable, and `whisper.cpp` on the weakest hardware. Third, record not just wall-clock and memory but **correction burden**: percentage of segments edited, proper-noun correction rate, number of catastrophic hallucination/repetition events, and time to produce usable notes. The winning PoC choice is the configuration that minimises *total user burden*, not merely raw WER.

The provider contract should therefore persist, per transcript generation, the provider name, checkpoint, quantisation, device type, decode parameters, detected language, and timestamp mode. That makes regression testing much harder to fake and much easier to trust. It also allows the architecture to make a disciplined decision later: if the weakest supported machine collapses under the primary configuration, the answer is to **switch provider or checkpoint for that machine tier**, not to undo the provider abstraction.

The resulting decision is clear enough to unblock work now: **choose `faster-whisper` as the primary local ASR provider, operate with `large-v3-turbo` by default, retain `large-v3` as a quality rerun target, and keep `whisper.cpp` available as the first fallback provider for weaker or more brittle environments.** Parakeet is worth a later specialist comparison only if product scope narrows toward English and standardised NVIDIA hardware; Vosk stays on the edge of the shortlist for extreme low-spec or vocabulary-driven cases.
