## Recommended baseline

PoC v0 should use dedicated `stdio` between the orchestrator and the capture worker, with the orchestrator spawning or directly supervising the worker as a child process. In practice that means: orchestrator-to-worker traffic on the child’s `stdin`, worker-to-orchestrator traffic on the child’s `stdout`, and `stderr` reserved for diagnostics only. Pipes are the standard IPC channel for related processes, and mainstream runtimes expose exactly this stdin/stdout/stderr piping model for child processes. citeturn15view0turn12view0turn12view1turn12view2

The wire format should be compact UTF-8 JSON, one top-level object per LF-terminated line. Pipes are byte streams and do not preserve message boundaries, so framing is mandatory. JSON is explicitly minimal, portable and textual, and JSON strings cannot contain raw control characters such as line feed unless escaped, which makes one-line framing robust as long as the encoder emits a single compact object per message and the decoder buffers until LF. Do not pretty-print on the wire. citeturn15view1turn7view0turn8view0turn8view1

The protocol should carry live coordination only: start and stop commands, readiness, state transitions, errors, fact proposals, status, and references to durable artefacts that have already been written to disk. It should not carry raw audio, binary blobs, large transcript bodies, or canonical session-record snapshots. Official runtime documentation for Python, Node and Rust all warns that piped subprocess I/O can block or deadlock when buffers are not drained, which is another reason to keep frames small and push bulky data into files. citeturn13view0turn13view2turn12view1turn12view2

## Why stdio wins

Against your ordered criteria, `stdio` wins first on implementation simplicity. It needs no bind/listen/connect cycle, no local socket pathname, no cleanup of transport endpoints, and no extra abstraction beyond the child-process relationship you already have. That keeps the design small, testable, and aligned with a supervisor-owned worker lifecycle rather than nudging the application towards a service-style topology. citeturn15view0turn12view0turn12view1turn12view2

It also gives unusually clear failure semantics for a PoC. `pipe(7)` is explicit that pipes are byte streams with no message boundaries, that reads see EOF when the write end is closed, and that writes raise `SIGPIPE` or fail with `EPIPE` when the read end is gone. Those are exactly the signals you want for “the peer exited”, “the peer disconnected”, and “the transport is broken”. The practical hazard is backpressure: a full pipe blocks writers, and official Python, Node and Rust docs all warn that a child can block or deadlock if piped output is not consumed. That argues for dedicated reader loops, small messages, immediate closure of unused duplicate descriptors after spawn, and a hard rule that protocol traffic never shares a stream with human logs. citeturn15view1turn2view0turn13view0turn13view2turn12view1turn12view2

Observability is another strong point. JSON’s textual nature makes local transcripts readable, diffable and easy to snapshot in tests. Keeping `stderr` separate means the protocol stream stays machine-parseable while diagnostics remain human-oriented. In a privacy-first product, that should translate into two debug levels: metadata traces by default, and opt-in full-frame capture only when debugging protocol faults. citeturn7view0

For the same reason, I would not add heartbeats in v0 unless you already have evidence of live-but-stuck workers that cannot be detected by startup timeouts, shutdown timeouts, exit codes, and EOF/EPIPE. The operating system already supplies strong peer-death signals over pipes; the first version should exploit those before inventing another liveness mechanism. citeturn2view0turn15view1

## Second-best alternative

The runner-up is a local Unix-domain socket pair on POSIX, preferably `socketpair(AF_UNIX, SOCK_SEQPACKET, ...)`, with the same UTF-8 JSON envelope on top. `socketpair()` gives you an unnamed connected pair of sockets; `SOCK_SEQPACKET` is reliable, bidirectional, connection-oriented, and preserves record boundaries, so a sent record maps naturally to a received record. Unix-domain sockets can also pass file descriptors or credentials if you later need that. citeturn2view3turn11view2turn11view3turn11view0

That is still second-best for the current PoC because it solves a problem you do not yet have. It adds transport-specific setup and platform nuance, and if you move from unnamed socket pairs to pathname sockets you also inherit endpoint lifecycle, directory permissions, and unlink cleanup. The Linux documentation is explicit that binding a pathname socket creates a filesystem entry that the caller must delete when it is no longer needed. For a single local worker under direct supervision, that is gratuitous complexity. citeturn11view0

I would reach for Unix-domain sockets only if one of two things becomes true: the worker must attach outside the immediate parent-child spawn path, or message-boundary preservation and ancillary features such as FD passing become materially valuable. If neither is true, `stdio` remains the smaller and clearer tool.

## Versioning and boundary rules

The minimal versioning contract should be connection-level, explicit and fail-fast. The first protocol message should be a `hello` carrying at least `protocol_major`, `protocol_minor`, `role`, and optionally a build identifier. Every subsequent frame should be a single top-level object with a stable envelope such as `v`, `type`, `id`, `session_id`, and `payload`. Incompatible changes bump the protocol major and should fail the session immediately. Compatible changes within a major may add optional fields, but unknown message types should be treated as protocol errors rather than silently ignored, because orchestrator and worker ship together and silent drift will hurt debugging more than it helps compatibility.

Durable file schemas must be versioned separately from the live protocol. The protocol exists only for coordination; files exist for long-lived artefacts. That means every artefact reference should carry its own file-schema version in both the file metadata and the `artifact_ready` payload, alongside integrity metadata such as a digest and logical kind. If something matters after a crash, it must already exist durably in a versioned file before the protocol announces it.

That boundary also answers what should not go through the protocol. The worker should not stream raw audio, PCM chunks, large transcript payloads, or rewrite the canonical session record. It should emit observations and references. The orchestrator, while it holds session authority, remains the only component that turns those observations into canonical durable state.

I would also avoid full JSON-RPC in v0. JSON-RPC is a clean and lightweight RPC protocol, and it explicitly distinguishes notifications from request/response pairs. The Language Server Protocol then adds `Content-Length` header framing on top of stdio. Those are sensible precedents if this link later grows into a richer bidirectional method API, but they are extra machinery for a small internal command/event protocol whose immediate need is coordination, not a general RPC surface. citeturn1view4turn14view0turn14view2turn2view6turn2view7

## Testing posture

The protocol boundary should be tested with the discipline of a public interface even though it is private. Keep the wire codec separate from business logic. Write a short normative protocol note. Check in golden fixtures for each message type and lifecycle transition. Test round-trip encode/decode, unknown-version rejection, malformed JSON, truncated frames, oversize messages, missing required fields, illegal state transitions, unexpected EOF, and orderly shutdown. That gives parallel implementers a shared contract without prematurely committing the project to code generation or a heavy IDL.

The most important testing choice is transport realism. At least one integration suite should spawn a real worker and talk over actual stdio, not an in-memory mock. The reason is practical: Python, Node and Rust all document that piped subprocess I/O can block or deadlock when output is not drained, and `pipe(7)` likewise warns that full pipes block writers and that applications should be designed so readers consume promptly. Real-process integration tests are the cheapest way to catch exactly the class of bug that abstract unit tests tend to miss. citeturn13view0turn13view2turn12view1turn12view2turn15view0

For observability, tests should assert two layers. First, the transport contract: frame boundaries, decoding, correlation ids, shutdown, and error classification. Second, the operator story: exit codes, `stderr` diagnostics, protocol transcript metadata, and the orchestrator’s recovery or termination behaviour when the worker misbehaves. In a privacy-first product, default traces should record direction, type, ids, sizes and result codes; full payload capture should be explicit and temporary. citeturn12view0turn12view1

## Future evolution triggers

There are three clean upgrade steps before any large framework jump. If line-delimited JSON starts to feel too ad hoc, but you still want a textual wire format, RFC 7464 JSON Text Sequences is the natural next framing step: it is a standard UTF-8 framing format, uses record separators, and explicitly allows parsers to recover from malformed or truncated elements. If you still like stdio but need richer request/response semantics or capability negotiation, the next step is LSP-style `Content-Length` framing with a lightweight RPC convention. If the problem is transport topology rather than framing, move first to a Unix-domain `socketpair()` or local socket instead of changing the message schema. citeturn9view2turn9view3turn2view6turn2view7turn11view0turn11view2turn11view3

Stronger schema tooling is justified only when the protocol becomes infrastructure rather than a narrow internal seam. Concrete triggers would be multiple workers or languages, repeated compatibility pain, generated bindings becoming clearly cheaper than hand-maintained validators, or a message catalogue large enough that fixtures and manual codecs become the maintenance bottleneck. That is where Protocol Buffers start to earn their cost: they are designed as a language-neutral, platform-neutral, extensible structured-data system with generated code and explicit field-evolution guidance. citeturn16view0turn16view1

Only if the product later grows a genuine service-style RPC surface with unary and streaming calls should gRPC enter the discussion. Its official model is built around generated client and server code and supports unary, server-streaming, client-streaming and bidirectional-streaming RPCs. That is useful power, but it is clearly beyond the needs of a private local coordination channel for one orchestrator and one capture worker. citeturn16view2

On the facts available, none of those triggers seems present yet. The architecture wants enough rigour for parallel implementation and contract testing, without turning a local product into a miniature distributed system. Strict but boring stdio plus compact JSON is exactly the right fit for that shape of problem.

## Open questions and limitations

The main limitation in this note is repository visibility: I could not inspect `docs/architecture/architecture-overview.md` or `docs/architecture/implementation-guardrails.md` in this chat, so I could not verify whether there are language-runtime constraints that might slightly tilt the framing choice, such as Windows-specific stdio behaviour, a non-child worker launch model, or near-term need for FD passing. If those documents reveal any of those conditions, the transport should be revisited. Otherwise, the decision is straightforward:

Use dedicated stdio for PoC v0, compact UTF-8 JSON with one object per LF-terminated line, an explicit but minimal versioned envelope from day one, files for all durable or bulky data, and real transport-level contract tests. The second-best alternative is a POSIX Unix-domain `socketpair()` with `SOCK_SEQPACKET` when topology or record-boundary needs genuinely appear.
