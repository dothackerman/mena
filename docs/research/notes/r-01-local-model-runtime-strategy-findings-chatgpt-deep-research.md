# R-01 Local Model Runtime Strategy

## Executive recommendation

For the current PoC, `mena` should default to an **application-owned local runtime adapter built on `llama.cpp`, run out of process as a tightly owned `llama-server` subprocess for the lifetime of a workflow job or batch**. The important distinction is *not* “library vs HTTP” in the abstract; it is **owned, explicit, local lifecycle control** versus dependence on a user-managed shared daemon. `llama.cpp` is the strongest fit for that shape because the project’s main product is the `llama` library, but it also ships an OpenAI-compatible HTTP server with chat, responses, embeddings, schema-constrained JSON, monitoring endpoints, extensive threading/context controls, and broad backend coverage across CPU, CUDA, HIP, Vulkan, and CPU+GPU hybrid offload. It also supports prebuilt binaries, build-time backend selection, and dynamic backend loading, which matters for shipping a Linux-first PoC that must still survive on mismatched tester hardware. citeturn23view0turn7view1turn11view0

Within that recommendation, I would **not** embed the runtime directly into the main application process for the first PoC unless later evidence shows subprocess startup is the real bottleneck. Given the brief’s priority order, the safer shape is: start a job-scoped local runtime process, keep it warm during the note-generation chain, capture its stdout/stderr and timings, then shut it down cleanly. That gives better failure inspection and better fault isolation than in-process native inference, while still keeping the runtime fully under the product’s control. The lack of a strict post-meeting latency target makes this trade-off acceptable. citeturn23view0turn7view1

The **second-best option is Ollama**. It is a credible fallback because it has straightforward Linux installation and updating, documented systemd service setup, clear journal-based logs, structured outputs, native usage metrics, GGUF import and quantisation paths, and a documented local-only mode even though it now also has cloud features. It loses to an owned `llama.cpp` subprocess because it is still a separate daemon with its own shared model store, queueing and residency behaviour, and an optional cloud surface that `mena` would need to constrain deliberately. That makes it slightly worse on hermetic automation, failure clarity, and preserving a clean runtime port boundary. citeturn4view0turn25view0turn20view0turn26search0turn5view5turn19view1turn24search2

On **local summarisation viability**, my working conclusion is: **yes, it is viable on the first target laptop if that machine is roughly in the “modern developer laptop” class, but the recommendation is hardware-conditional because the brief does not specify exact specs**. A sensible default is a **3B–4B quantised instruct model**, with a **1B–3B fallback profile** for weaker testers and a **7B profile only for machines with comfortable memory headroom or useful GPU offload**. Current packaged model sizes illustrate why: Llama 3.2 3B is around 2.0GB in a common Q4 package and is positioned for summarisation, Qwen2.5 3B is about 1.9GB, Gemma 3 4B is about 3.3GB and is positioned for resource-limited deployment, while Qwen2.5 7B is already about 4.7GB and 12B-class packages are around 8.1GB before context and runtime overhead. citeturn13view2turn14view0turn13view3turn13view1

## Why the recommendation wins

The owned `llama.cpp` route best preserves the **clean provider/runtime boundary** the brief is asking for. Every serious option in this comparison can be reached through a localhost API of some kind: `llama.cpp` provides OpenAI-compatible chat, responses and embeddings; Ollama exposes native APIs and OpenAI-compatible endpoints; LM Studio exposes both native REST and OpenAI-compatible endpoints; LocalAI positions itself as a drop-in OpenAI-compatible local API; and vLLM does the same for server deployment. That means `mena` should keep an **application-specific runtime port** and treat “OpenAI-compatible HTTP” as an *internal adapter detail*, not as the architectural boundary itself. That is easiest to do when the product owns the runtime process rather than binding itself to one external desktop/runtime product. citeturn7view1turn4view1turn5view2turn4view6turn1search15

The owned `llama.cpp` route is also the safest baseline for **mixed and weaker Linux hardware**. `llama.cpp` explicitly targets a wide range of hardware, supports integer quantisation, AVX/AVX2/AVX512 on x86, and offers CUDA, HIP, Vulkan and CPU+GPU hybrid offload. Ollama is also reasonably strong here: its troubleshooting docs show distinct CPU libraries for `cpu`, `cpu_avx`, and `cpu_avx2`, and its hardware docs support older entity["company","NVIDIA","gpu vendor"] GPUs down to compute capability 5.0 while also covering many Linux entity["company","AMD","chipmaker"] GPUs through ROCm. By contrast, LM Studio’s x64 Linux baseline requires AVX2, recommends at least 16GB RAM, and says Ubuntu versions newer than 22 are not well tested. That combination is good enough for an optional adapter, but not the safest starting point if weaker testers are a first-class constraint. citeturn7view0turn25view0turn10view0turn4view4

It is also the most **hermetic** option for CLI-driven automation and agent-driven testing. With an owned subprocess, tests can pin an exact runtime binary, fixed model file, fixed flags, fixed port, and temporary cache/model directories, then kill and restart the runtime deterministically while collecting stdout, stderr and structured timing output. Shared daemons are scriptable, but less inherently self-contained. Ollama’s Linux docs and FAQ describe a system service and a shared default model location under `/usr/share/ollama/.ollama/models`, with an environment-variable override if needed. LM Studio stores models in `~/.lmstudio/models` and has JIT loading, TTL and auto-evict behaviour that changes model residency unless it is normalised deliberately. Those are solvable issues, not fatal flaws, but they are more moving parts than a job-owned subprocess. citeturn24search2turn21search0turn21search2turn28view0turn28view1

This is why **Ollama is second-best rather than first**. Its operational story is genuinely good for Linux PoCs: installation and upgrades are scripted, startup as a systemd service is documented, logs are easy to inspect, concurrency and queueing behaviour are documented, usage timing fields are returned by the API, structured outputs are supported, and local-only mode is documented even though cloud features now exist. If the product team cannot reasonably own runtime packaging in the current PoC window, Ollama is the pragmatic fallback I would choose. But as soon as the architecture value of explicit lifecycle control, hermetic tests, and minimal product coupling becomes the priority, the external daemon loses by a narrow but meaningful margin. citeturn4view0turn25view0turn10view1turn26search0turn5view5turn19view1

**LM Studio is better than it used to be for headless use, but it still loses more clearly.** The 2026 story is no longer “GUI only”: `llmster` exists as a standalone daemon, `lms` can start the daemon and HTTP server, Linux systemd startup is documented, log streaming is good, the native REST API exposes model load/download/unload endpoints and useful stats, and `lms load --estimate-only` is genuinely attractive for capability checks. The reason it still loses is fit, not capability. It brings more product surface than this PoC needs, its Linux support assumptions are tighter, and its default JIT/TTL/auto-evict behaviours mean more hidden state unless the adapter takes control explicitly. citeturn28view1turn16view0turn16view1turn5view4turn27search0turn28view0turn4view4

I included **LocalAI** and **vLLM** because they are the only “other” candidates that represent materially different runtime families rather than just alternative wrappers. LocalAI is effectively a general-purpose local AI control plane: multi-backend, OpenAI-compatible, container-first, and broad enough to cover text, audio, images and more. That breadth is precisely why it is not a good default here. vLLM is a serious OpenAI-compatible serving engine and belongs in any honest comparison, but its docs are still oriented toward Linux server environments, higher-end GPU paths, and Docker/source builds for some hardware. Both are real options; neither is the best current PoC baseline for a Linux-first, local-first, weak-hardware-aware meeting-notes tool. citeturn8search0turn8search2turn18view0turn18view2turn4view7turn5view0turn1search15

## Local summarisation viability

The most important point here is that **runtime choice is not the main determinant of viability on weaker machines; model size and context discipline are**. Current packaged sizes show the rough shape of the problem: around 0.8–1.0GB for 1B/1.5B models, around 1.9–2.0GB for 3B models, around 3.3GB for Gemma 3 4B, around 4.7GB for Qwen2.5 7B, and around 8.1GB for 12B-class packages. Model pages for Llama 3.2 and Gemma 3 also explicitly position these families for summarisation or compact local deployment. So the runtime shortlist matters, but the first-order control is still “how big is the model package, and how much context are you trying to hold?” citeturn13view2turn13view3turn14view0turn13view1

My working judgement for the PoC is therefore:

- **First target laptop, assuming a modern Linux developer laptop with roughly 16GB+ RAM:** local summarisation is very likely viable with a **3B–4B quantised model** running CPU-only if needed; **7B** is plausible but should not be the default unless the machine has clear memory headroom or useful GPU offload. I would not make **12B** the baseline for a mixed-hardware PoC. This is an inference from current model sizes and Linux desktop guidance, not a measured benchmark. citeturn14view0turn13view1turn4view4
- **Weaker representative tester, roughly 8GB RAM and no discrete GPU:** local summarisation is still plausible, but only with **1B–3B profiles**, conservative context lengths, and serial post-processing. A 4B model may work on some machines, but I would treat it as a risk rather than a safe default; 7B is too close to the edge for a baseline expectation. citeturn14view0turn13view1turn10view1
- **Older x64 testers without AVX2:** LM Studio should not be the architectural baseline. The safer paths are the owned `llama.cpp` runtime or Ollama, because they explicitly expose broader CPU-path compatibility than LM Studio’s AVX2-only x64 baseline. citeturn7view0turn25view0turn4view4

The context story matters just as much as model size. Ollama’s docs say required RAM scales with the product of parallelism and context length, and its default context behaviour is reduced substantially on systems without large VRAM. LM Studio, for its part, exposes explicit context-length controls and a pre-load memory estimator. So architecture should **not** assume “the model advertises 32K or 128K, therefore we can dump a whole corrected meeting transcript into one request.” For the current PoC, the safe design is **chunked map-reduce summarisation, then a small merge pass, then targeted coherence or action-item checks**. That design is more robust on weak hardware and makes runtime replacement less important than it would be in a monolithic single-prompt design. citeturn10view1turn26search4turn27search0

## Architecture boundary implications

The runtime adapter boundary should be shaped around **capabilities and policy**, not around any vendor API. I would separate it into two ports.

The first port is an **inference port** for stage execution. It should accept an application-level request such as: stage kind, model profile, input artefact references, requested output schema, resource budget, timeout, and locality requirement. It should return typed outputs plus execution metadata. The important thing is that workflow code should ask for “structured summary” or “semantic consistency check”, not for `/v1/chat/completions`, `ollama chat`, or `lms load`. The fact that `llama.cpp`, Ollama, LM Studio, LocalAI and vLLM all overlap on a portable stateless inference subset is what makes this realistic. citeturn7view1turn4view1turn5view2turn4view6turn1search15

The second port is an **admin/preflight port**. That is where runtime-specific operations belong: health checks, model-availability checks, resource estimation, model import or preparation, and structured failure inspection. LM Studio’s estimate-only load path is a good example of why this should be separate from hot-path inference. Ollama’s model import, quantisation and residency controls are another example. These are useful runtime tools, but they should not leak into the workflow layer as if they were business concepts. citeturn27search0turn20view0turn10view1

Internally, I would standardise on a **lowest-common-denominator localhost invocation subset** even if the product never exposes it directly: explicit model identifier, stateless request/response, structured JSON when schemas are needed, embeddings when needed, and explicit context/max-token controls. That recommendation is strengthened by the fact that Ollama’s OpenAI Responses support is explicitly non-stateful, while LM Studio also offers richer stateful APIs. The architecture already has an artefact-first pipeline, so state belongs in `mena`’s artefacts and orchestration metadata, not in runtime-managed conversation state. citeturn4view1turn5view4

For supportability, the adapter should always emit a **failure envelope** with at least: runtime family, runtime version, model identifier, model path or digest, command or base URL, context length, GPU-offload mode, timing fields, exit code or HTTP status, stderr excerpt or log pointer, and whether the call was strictly local-only. That recommendation is directly aligned with the available observability surfaces: `llama.cpp` has monitoring and performance controls, Ollama exposes logs and usage timings, and LM Studio exposes log streaming, model/runtime metadata and stats. citeturn7view1turn26search0turn16view1turn16view3

One final architectural implication: **do not let default runtime configuration quietly widen the trust boundary**. If an LM Studio adapter exists, keep it on localhost, keep authentication explicit if network access is ever enabled, and do not rely on permissive CORS or local-network serving as defaults. If an Ollama adapter exists, treat local-only mode as part of the adapter contract and prevent cloud-model use in this PoC path. citeturn28view2turn19view1

## Risks and validation work

The recommendation is strong enough to unblock the PoC, but it is **not settled enough to become silent architecture fact**. The biggest unresolved variable is hardware: the brief does not specify the first target laptop, and the three referenced repository documents were not available in the conversation to cross-check against the brief. So this note should be treated as **official-runtime-informed and decision-quality, but still conditional on actual machine tests**.

There is also a real **version-pinning risk** with the preferred option. `llama.cpp` explicitly tracks changes to both the public library interface and the `llama-server` REST API in separate changelogs, and downstream consumers are told to check those before upgrading. That is not a reason to reject it; it is a reason to treat the runtime binary and its model artefacts as pinned dependencies, not floating infrastructure. citeturn22search2turn7view0

The **installation and support burden** shifts depending on the option. With an owned `llama.cpp` runtime, the burden shifts from end users to the product team: you own a pinned runtime binary, backend packaging, and model storage under runtime data directories outside the repo. With Ollama, the burden shifts more to the machine operator: install/update a separate service, manage its shared model store, and keep local-only policy enforced. With LM Studio, operators may need either the desktop app or `llmster`, and runtime downloads are a separate concern from app installation. With LocalAI and vLLM, the burden is even more obviously “operator/devops shaped” because containers, backend configuration, or higher-end GPU/server assumptions are part of the normal setup story. citeturn4view0turn24search2turn28view1turn19view0turn8search0turn5view0

The validation work I would run before treating the choice as settled is short and concrete:

- Build a minimal owned-runtime prototype around **job-scoped `llama-server`**, not full in-process embedding.
- Test one structured-summary stage and one smaller coherence-check stage on three representative machine classes: a likely first-target laptop, a 16GB no-dGPU tester, and an 8GB weaker tester.
- Compare **1B, 3B, 4B and optional 7B** profiles using the same corrected transcript artefacts and the same output schema.
- Inject obvious failures: kill the runtime mid-stage, deny model-path permissions, simulate out-of-memory behaviour, and test absent or broken GPU drivers.
- Implement an **Ollama adapter** next, to confirm that the proposed port boundary really is replaceable.
- Treat **LM Studio `llmster`** as an optional third adapter only if there is a concrete reason to support it, not because it is interesting in the abstract.

If that validation shows the owned `llama.cpp` path is too costly to package in the current PoC window, the architecture fallback should be: **keep the same port boundary, switch the default adapter to Ollama temporarily, and preserve the same model-profile strategy**. In other words, the first fallback for weak machines should usually be **smaller model profiles and tighter context budgets**, not a wholesale change of runtime family.
